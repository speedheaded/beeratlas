# Пивной атлас Праги

Справочник чешского пива и пивоварен с подбором по формуле «отклонение от
знакомого якоря» и привязкой к пражским заведениям.

Стратегия и решение по развилке — в [BRIEF.md](BRIEF.md).
Это описание технической основы, которая нужна всем трём путям одинаково.

---

## Что здесь моат, а что нет

**Каталог сортов моатом не является.** Его сгенерирует кто угодно за выходные.

Защищает связка, которую нельзя сгенерировать, только собрать:

- где сорт реально налит (через пивоварню, а не через SKU)
- сегодняшняя цена за 0,5 л
- групповая проходимость заведения
- дата последней проверки

Поэтому связь «заведение ↔ пивоварня» — не поле в конце карточки, а ось схемы.

---

## Ключевые решения

### 1. Провенанс на каждом значимом поле

Любая цифра несёт метод получения, источник и дату:

| Метод | Что значит |
|---|---|
| `official` | сайт пивоварни, этикетка, официальный список заведений |
| `measured` | увидено или замерено лично |
| `phone` | спросили по телефону |
| `inferred` | выведено моделью — **самый слабый уровень** |
| `unverified` | заполнено по памяти, требует проверки |

Значения уровня `inferred` и `unverified` помечаются в интерфейсе визуально.
Без этого база превращается в правдоподобно выглядящую выдумку, и первый же
гид это заметит — а он тут единственный эксперт, чьё доверие нельзя потерять.

### 2. Вкус задаётся относительно, а не абсолютно

Девять осей 0–10, но заполняются как позиция относительно центроида стиля.
Иначе у всех hazy IPA получится один вектор — потому что маркетинговые
описания у них написаны одинаково.

Девятая ось специфична для Чехии: `hopProfile`, где 0 — классический жатецкий
травяно-пряный, 10 — новосветский цитрусово-тропический. Здесь главный вопрос
не «сколько хмеля», а «какой».

### 3. Подбор через якорь

Пользователь не отвечает на «сухость от 1 до 10» — он не умеет. Он берёт пиво,
откалиброванное у него во рту, и двигает его:

```
Урквелл  →  [менее горькое −2]  [темнее +3]  →  Kozel Černý
                                                 «как Урквелл, но заметно
                                                  сладкое солодовое, жжёное»
```

Один и тот же механизм работает в двух режимах: `findMatches()` ищет
существующее пиво и где оно налито, `describeSpec()` описывает гипотетическое
для опроса о варке.

Оси, которые пользователь тронул, весят при подборе больше — если человек
специально убавил горечь, промах по горечи наказывается сильнее.

### 4. Нет заведения — нет страницы сорта

`findMatches()` по умолчанию отфильтровывает пиво, которое негде выпить
(`requireVenue: true`). То же правило действует при публикации: сорта без
привязанного заведения живут строкой в линейке на странице пивоварни, а
отдельной страницы не получают.

## Порядок работ

Сначала интерфейс на двадцати записях, потом масштабирование данных. Если
взаимодействие плохое на двадцати сортах, на четырёхстах оно лучше не станет.

1. **Обзвон 60 заведений** — групповая проходимость. Данных нет ни у кого,
   потому что их нельзя сгенерировать. Первое, что показывают гиду.
2. **Граф «пивоварня ↔ заведение»** из официальных списков партнёрских
   заведений; гео и часы — из Google Places (в сиде координаты нулевые).
3. **Один экран:** якорь → ползунки → результаты → где налито.
4. **Карта** — Leaflet поверх OpenStreetMap, без платных ключей.
5. **Масштабирование каталога** агентами: ~60 пивоварен, 300–400 сортов.
   Каждое поле с провенансом, `inferred` проверяется выборочно.

## Стек

Файлы вместо базы, пока это возможно. 400 сортов и 250 заведений — это
несколько сотен килобайт JSON: фильтрация уходит на клиент, git даёт историю
и ревью сгенерированных данных в диффах.

Postgres появляется тогда, когда появятся правки гидов, опрос и пользователи —
не раньше. `pgvector` понадобится только для текстовых эмбеддингов описаний;
для девятимерного вектора вкуса полный скан быстрее любого индекса.
